## Findings (verbatim, unedited)

1. R1-1 — BLOCKER — `harness/upstream014.py:42-100`, Decision D-1. The wrapper hashes the intended Study 014 files but then uses bare imports for `verify`, `commitment`, and `owpflow`; an earlier `sys.path` entry or preloaded `sys.modules` object can therefore execute unpinned code while `problems()` reports no mismatch. The clean-environment assertion in `harness/tests/test_study.py:30-43` is not a governing-scorer gate. This defeats `PREREGISTRATION.md` §2’s claim that pinned 014 code necessarily runs unchanged. Fix: load every upstream module from its authenticated absolute path under private aliases, reject pre-existing collisions, and verify each loaded module’s resolved origin and digest on every load, including cached loads.

2. R1-2 — BLOCKER — `PREREGISTRATION.md` §1/§4/§4c; `harness/MATRIX.json:85-90`; `harness/build_fixtures.py:298-309`. `cur-authz-rollback-accepted` does not construct rollback: it exactly reproduces Study 014’s alternative-valid-WorkOrder remint, changing only quota `100/1` to `200/2`; the purported acceptance-criteria update is a no-op, and no version, ordering, retirement, or “older” marker exists. Study 014 expressly kept e22 descriptive and outside R1 (`studies/014-openworkproof-binding/PREREGISTRATION.md:424-427`, `MATRIX.json:167-172`, `DEVIATIONS.md:20-22`), while RFC 0011’s accepted R-1 disposition removed it as evidence and a conformance vector (`spec-main/rfcs/reviews/0011-round-1.md:109`). Its all-pass expectation follows, but cannot establish authorization-contract rollback. Fix: rename it “alternative valid WorkOrder remint accepted,” restore descriptive/no-credit status, and scope inverse expectations to CURRENCY; a real rollback endpoint needs an independently ordered authorization anchor.

3. R1-3 — BLOCKER — `registry/verify_currency.py:97-118,193-241,262-284`; `registry/SPEC.md` §§2–4. The supposedly exhaustive, fail-closed verifier accepts or crashes on malformed readable JSON outside its vocabulary. Plain `json.loads` accepts duplicate members; canonicalization occurs before type validation and outside an exception boundary; signed attestation payloads never have their own `snapshotVersion` checked; checkpoint scalar types and digest formats are unchecked; and a malformed non-object `persistedMinimumHead` is silently treated as absent. Thus duplicate-key bytes can verify as their last-wins object, huge/non-JCS values can raise, an authority-signed version-2 attestation payload can pass, and malformed rollback state can disable the floor. Fix: use duplicate-rejecting strict JSON, enforce exact closed schemas and scalar formats before canonicalization/folding, catch canonicalization/type failures into registered codes, require exactly object-or-null minimum state with non-boolean integer positions, and add adversarial ordering/crash vectors.

4. R1-4 — BLOCKER — `harness/score.py:354-374`; `PREREGISTRATION.md:174-180,211-215`; `README.md:26-30`. The built split views are a genuine same-key, same-genesis, same-position fork (`harness/build_fixtures.py:145-155`), but the scorer never validates those facts: it calls any differing currency strings “contradictory” and hardcodes `forkRevealedToEitherRun: false`. The accompanying impossibility claim is also too broad: `harness/tests/test_registry.py:194-202` shows that an offline invocation supplied the previously accepted sibling head rejects the same-length fork. What is impossible is detection by a fresh, stateless, two-pin verifier given exactly one view—not by every offline verifier or run. Fix: validate the fork structurally from bytes, derive or remove the reveal field, narrow all impossibility wording, and separately register a sequential A→B stateful arm.

5. R1-5 — MAJOR — `registry/verify_currency.py:165-166,269-307`; `harness/run_verify.py:78-99`; `harness/build_fixtures.py:357-365`. `persistedMinimumHead` is not persisted by the verifier: it is merely a caller-supplied third anchor, and the layer returns no authenticated state update. `cur-older-snapshot-pinned` fabricates a position-3 minimum beside a position-2 presentation rather than first accepting position 3, durably updating state, restarting, and receiving position 2. It therefore demonstrates conditional prefix comparison, not RFC 0011’s persisted high-water lifecycle (`rfcs/0011-judgment-currency-anchor.md:200-207,304-306`). Offline operation is not the problem; local durable state is compatible with it. Fix: implement atomic accepted-head persistence and sequential rollback/fork tests, or rename this input `minimumHeadPin` and narrow the claim to caller-provisioned state.

6. R1-6 — MAJOR — `registry/checkpoint.py:111-116,148-157`; `registry/verify_currency.py:79-94`; `registry/SPEC.md:115-121,165-166`. `authorityKeyId` is outside the signed payload, yet first-failure attribution trusts that unauthenticated string before signature math. Relabeling a pinned-key-valid record produces `snapshot-authority-unpinned`, while labeling a foreign signature with the pinned ID produces `snapshot-signature-invalid`; therefore the registered meanings “signed under an unpinned authority” and “signature under the pinned key is invalid” do not describe cryptographic signer identity. Fix: either verify only under the pinned key and collapse the distinction, or carry and authenticate signer key/delegation material, derive its ID, and then compare that authenticated identity to the trust mapping.

7. R1-7 — MAJOR — `rfcs/0011-judgment-currency-anchor.md:286-303`; `rfcs/reviews/0011-round-1.md:121`; `registry/verify_currency.py:193,215-241,288-303`. RFC 0011 R-13 requires concrete snapshot-byte, event-count, and current-set limits with at-limit and one-past-limit refusal vectors. Study 016 defines none: it decodes the complete document and verifies/folds an unbounded record list. This silently drops an accepted security prerequisite while describing the ceremony as fail-closed. Fix: register and enforce pre-parse byte and in-fold work/set limits, add an exact resource-limit verdict, and include boundary and adversarial tests; otherwise explicitly exclude resource safety from the prototype’s claims.

8. R1-8 — MAJOR — `PREREGISTRATION.md:153-157,298-299`; `harness/MATRIX.json:13-135`. The matrix cannot support either “each verification family is alive” or “the chain layers replicate 014’s result under a new evaluator release.” BINDING and REPLAY expect `pass` in all 20 cells, so implementations hardcoded to pass would satisfy the entire matrix; only OWP has one negative chain control. Study 014’s frozen result covered many BINDING- and REPLAY-owned refusals (`studies/014-openworkproof-binding/ANALYSIS.md:47-72`), none of which are rebuilt here under v0.17.0. Fix: say only that 016 reuses the pinned adapter and demonstrates positive compatibility on its four chains, or add distinct v0.17 BINDING-fail and REPLAY-fail controls; claiming replication of 014’s result requires rebuilding its mutation stratum.

R1-9 — MAJOR — `harness/MATRIX.json:5-8,61-65,106-111`; `harness/build_fixtures.py:339-340,357-359`; `harness/score.py:520-529`. `cur-concurrent-set` and `cur-older-snapshot-unpinned` are byte-identical endpoints with the same all-pass tuple. Those bytes contain no evidence that a newer snapshot exists, so the second row cannot empirically confirm withholding; it is the valid-concurrent-world observation plus an external scenario label, recreating the reason Study 014 removed e18 (`studies/014-openworkproof-binding/PREREGISTRATION.md:408-418`). 10. R1-10 — MAJOR — `PREREGISTRATION.md:109-113`; `harness/PINS.json:64-72`; `harness/build_fixtures.py:344-347`; `fixtures/cells/cur-series-unknown/trustconfig.json:4`. The preregistration says one genesis pin serves the matrix, but `cur-series-unknown` silently swaps the common `f5cf…` genesis for an other-series `b1b2…` trust root. With the stated common pin, the cell fails earlier as `snapshot-chain-inconsistent`, not `series-unknown-at-snapshot`; it is therefore not the registered registry-only contrast. This also exposes the implicit RFC R-9 mapping: the trust schema has no series identifier and applies whichever key/config the caller supplies to any commitment series (`registry/SPEC.md:83-99`, `verify_currency.py:183-189`). Fix: use a common global-log genesis capable of representing an unknown series, or register the second trust root and reclassify the mutation; additionally bind the trusted series/namespace in configuration or require a series-keyed trust-store lookup.

11. R1-11 — MAJOR — `harness/MATRIX-HOLDOUT.json:4-6`; `PREREGISTRATION.md:64-75`; `harness/score.py:487-519`. Once freeze pins are filled, an empty holdout is accepted and the scorer adjudicates only `MATRIX.json`, permitting `R1 holds` with `includeHoldout: true` despite the registered statement that emptiness is not passing and leaves postdictivity open. Conversely, any nonempty holdout currently terminates because no construction machinery exists. Fix before freeze: implement construction, adjudication, and separate reporting for the reviewer stratum; reject a registered empty holdout or publish an explicit holdout-absent/non-predictive verdict.

12. R1-12 — MAJOR — `harness/PINS.json:4`; `harness/score.py:450-478,531-559`; `PREREGISTRATION.md` §6. PINS says every attempt record carries `pinsSha256`, but `ATTEMPT.json` and terminal `RESULTS.json` omit it; only successful results contain the stamp. The scorer also claims `SystemExit` is recorded and re-raised, while lines 553-554 re-raise it without calling `terminal`. A non-replaceable primary attempt can therefore lack both a terminal result and the PINS identity needed to tie it to the external freeze anchor. Fix: hash raw PINS bytes into the initial marker before parsing, copy that hash into every terminal record, and terminal-record every post-marker `SystemExit`.

13. R1-13 — MINOR — `registry/verify_currency.py:139-161`; `registry/SPEC.md:130-136`; RFC 0011 §1. The fold accepts `[add(v,d), retire(v), add(v,d)]` and silently makes the version current again, even though the registered event vocabulary reserves `reinstate` for re-entry after retirement. This gives two lifecycle events the same effect and leaves the advertised state machine ambiguous. Fix: reject every later `add` of an already-bound version—different digest as `binding-rebound`, same digest as inconsistent—and require `reinstate`, or explicitly define `add` as a reactivation alias and add the missing vector.

Later limitations are correct but do not cure the primary wording. Fix: use the exact snapshot-membership formulation everywhere, restore the reliance/mapping language from RFC R-12, and remove “dated” unless a signed snapshot assertion time is added.

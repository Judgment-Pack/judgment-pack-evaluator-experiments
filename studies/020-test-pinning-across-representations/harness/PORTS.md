# Ports — what Study 020 takes, from where, and what changed

Study 020 is an **instrument repair on Study 019** (PREREGISTRATION.md §7): it
asks 019's question again with 019's machinery, and the machinery is inherited
as **bytes**, not as descriptions. This file records every port, its digest on
both sides, and exactly what was changed. `harness/integrity.py` machine-reads
the table below and binds each row **to the authority that row actually has**
before any call is made and before anything is scored.

The chain, with every link a pinned digest including both ends:

```
this file                                  (pinned in harness/PINS.json at port time)
    -> Study 019's harness/PINS.json            9ba6394d…  (pinned in harness/integrity.py
                                                            and in harness/PINS.json)
       Study 019's harness/PORTS.md             (the digest 019's OWN registry pins for it
                                                 under `ownPorts`, not one this study chooses)
       Study 019's harness/STUDY-MANIFEST.sha256
                                                (the digest 019's OWN registry pins for it
                                                 under `studyManifest`)
```

The port was taken at commit

```
commit e87e1311da11c28e929edf1e7e39f048e4ec0e6a
```

**Two source-side authorities, and this is the first port in the program that
has two.** Study 019 published a `PORTS.md` with seven destination cells and an
ADR 0004 **exact-set manifest** covering every byte it executes. The seven files
019 itself ported answer to BOTH — the ports cell and the manifest entry, which
`integrity.verify_chain()` requires to agree. The other thirteen answer to the
manifest alone, and that is not a weaker binding than a ports cell: 019's own
registry pins the manifest, so the digest comes from the source study either
way. What the manifest cannot supply is the *change list* a ports cell carries,
which is why those thirteen rows carry a full change list here rather than a
pointer.

**The commit is provenance, not authority.** Study 019 had one row —
`harness/make_manifest.py`, from Study 014 — bound to a recorded commit and to
nothing older, because Study 014 pinned none of its own harness sources. That
tier does not survive this port: the same file is bound here to 019's manifest
like every other row. No row in this table is satisfied by "whatever that commit
happened to hold".

**The lineage before 019 is HISTORY.** `harness/PINS.json`'s
`pinnedFrom.history` records Study 019's own `pinnedFrom` — Study 012's registry
digest `cff265e7…` and the Study 014 note — and `verify_chain()` checks that the
recorded history is the history 019's registry actually carries. It does not
walk into Study 012: a two-level walk would make this study's freeze depend on a
tree two studies away, and 019's own verification is what covers that level.

**This is a COMPLETE port of 019's executable harness surface and a PARTIAL
port of the study.** Every module 019's scorer, driver and wrapper execute is
here. What is NOT here is 019's *artifact* trees — the gold suite, both mutant
corpora, both reference implementations, the off-gold certificate, the
capabilities file, the verification documents — which §4.1 registers as ported
by digest and which `harness/SCAFFOLD.md` item **A1** carries as a
`GATE(pre-freeze)`. Every harness test that reads one of them SKIPS by a named
reason rather than passing vacuously, and `harness/PINS.json` records each
absent artifact's 019-side digest under a `…AtSource` member so the port is
checkable the moment the bytes land.

**One row can carry more than one source.** `integrity.REQUIRED_PORTS` fixes the
destination set at exactly the twenty files this table names, and
`verify_chain()` resolves a row's source-side authority **by its destination** —
so a second row naming `harness/batch.py` as its destination refuses, whatever
it names as its source. The count is read out of the constant by
`harness/tests/test_ports_chain.py` rather than out of a reader's memory, which
is Study 019's round-1 finding R1-20 applied to its own successor.

**New here, and deliberately absent from the table.**
`harness/e4lib/presence_idiom.py` is new in 020 (§3.2, ruling M-14): nothing
like it existed in 019, so a two-sided row would claim an inheritance that does
not exist. It is covered by the exact-set manifest like every other harness
source, and `integrity.REQUIRED_PORTS` names it not at all — which is the
loudest way to say it was not inherited. `harness/PINS.json`,
`harness/PORTS.md`, `harness/SCAFFOLD.md`, `harness/POWER-PRESENCE-IDIOM.md`
and `harness/STUDY-MANIFEST.sha256` are this study's own for the same reason.
